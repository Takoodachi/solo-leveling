## Project Overview

**Name:** Solo Leveling
**Type:** Personal workout + nutrition tracker with gamification
**Platform:** Progressive Web App (PWA), installed on iOS/Safari (friends); the owner uses an **Android app** that wraps the same live site (see *Android app*)
**Scope:** A small private group: the owner plus friends (6–7 users expected). **Each user's data is private**, except the **friends leaderboard**: every account publishes one snapshot (ranks, bodygraph, best lifts, level, streak, this week's training; never food, weight or notes) that all signed-in users can read. Sharing is on by default and can be switched off in Profile. Offline-first, with **optional per-user cloud sync** (the owner uses a phone + laptop). No app store deployment planned. **Infrastructure must stay on free tiers.**

> **History:** Started as a workout logger + calorie tracker. Workouts were removed in June 2026, then **reintroduced in September 2026** at the owner's request, together with a redesign (dark charcoal + orange/coral, mobile-first) based on reference mockups. Nutrition, body weight and steps remain first-class.

**Core principle:** This is a personal tool, not a product. Optimize for the owners' actual habits over generality. Avoid feature creep. Prefer simple, working code over abstraction.

## Tech Stack

- **Framework:** React 19 + Vite 8
- **Language:** TypeScript (strict mode)
- **Styling:** Tailwind CSS 3 + shadcn/ui components; fonts self-hosted via `@fontsource-variable/inter` and `@fontsource-variable/outfit` (no font CDN)
- **State:** Zustand for UI/ephemeral state (stores per domain: workouts (active session), auth, sync status)
- **Persistence:** Dexie.js (IndexedDB wrapper). Local-first; all data works fully offline
- **Sync/Auth:** **Supabase** (free tier). Email + password auth; per-user cloud sync. Gated by env vars; if unset, the app runs purely local. Users can also choose "Continue without an account" (local-only mode)
- **Charts:** Recharts
- **PWA:** vite-plugin-pwa (injectManifest, `src/sw.ts`)
- **Android app:** Capacitor 8 (`@capacitor/core`, `@capacitor/android`, `capacitor-health` for Health Connect, `@capacitor/local-notifications` for reminders and the rest timer) plus a small Kotlin plugin of its own; owner-only, sideloaded APK
- **Routing:** React Router v7
- **Icons:** lucide-react
- **Date utilities:** date-fns (not moment, not dayjs)
- **Hosting:** Cloudflare Workers static assets (free): `wrangler.jsonc` (SPA fallback via `not_found_handling`, **no `_redirects` file**, since Cloudflare rejects `/* /index.html 200`), `public/_headers`, `.nvmrc`. `netlify.toml` kept as a fallback One small Worker script (`worker/index.js`) answers `/api/*` only (`run_worker_first` in `wrangler.jsonc`): today that is the food search (see *Online food search*). Everything else is still served as static files without running any code.

**Do not add** Redux, MobX, or styled-components. Supabase is the only backend/auth dependency, beside the site's own Worker endpoint (a fixed proxy to one public search, no data of ours). Don't add others, and flag any new backend need instead of bolting it on. Anything paid (e.g. the Anthropic-backed `parse-food` Edge Function) must stay behind a flag and off by default (`VITE_ENABLE_AI_FOOD`).

## Navigation & screens

Bottom nav: **Home · [chosen] · (+) · [chosen] · Settings**. Home and Settings are fixed; the two middle slots are picked in Settings → Bottom bar (`settings.navTabs`, default Workouts + Analytics; choices: Workouts, Nutrition, Analytics, Strength = `/ranks`, Leaderboard, Profile; registry `components/navTabs.ts`, hook `useNavTabs`, cached in localStorage so launches don't flicker). Pages that can be tabs render inside `AppShell` (so `/ranks` and `/leaderboard` keep the bar) and show a back button only when they aren't in the bar (`useIsNavTab`). Profile lists every page that isn't in the bar (`ShortcutsCard`), so nothing is unreachable. The **+** opens a quick-add sheet: start/resume workout, log food, log weight, log steps, log water.

**Themes**: 18 preset palettes, 9 dark (Ember = default, Shadow Monarch, Abyss, Verdant, Blood Moon, Midnight Gold, Neon, Graphite, Volt) and 9 light (Daylight, Glacier, Matcha, Sakura, Iris, Lagoon, Honey, Cherry, Paper), in `features/settings/themes.ts`, plus **one of the user's own**. The first five of each are hand-tuned; the rest, and the custom one, come from `deriveTokens` in `themeBuilder.ts`: a whole palette from an accent, a background and the far end of the accent gradient (surfaces step away from the background, text takes a hint of its hue, white or dark text on the accent by contrast, and the carbs/fat/danger colours move aside when the accent lands on them). The custom theme is `settings.customTheme` (`{ mode, accent, background, gradient? }` as "H S% L%", synced) and is on screen when `settings.theme === 'custom'`; `cleanCustomTheme` pulls every colour into the range that stays readable for its mode (`CUSTOM_RANGES`), so read it through `resolveTheme` / `customTheme`, never raw. The editor (`CustomThemeEditor`, range sliders because the system colour picker isn't in every WebView) previews on the whole app with `paintTheme(…, false)` and puts the saved theme back when it closes. A theme sets the CSS variables on `<html>` (plus `carbs`/`fat` macro colours, `brand-from`/`brand-to` gradient, `ink`), toggles the `dark` class, and updates the browser theme-color. `settings.theme` syncs; `main.tsx` paints the last-used theme from localStorage before React renders (`applyCachedTheme`; the custom palette is cached beside the id); `useThemeSync` (App) follows the setting. **Colour rules so light themes work:** no raw `white`/`black` on app surfaces (use `foreground/NN` for hairlines and overlays, `primary-foreground` on `bg-primary`/`bg-brand-gradient`); macros use `text-carbs`/`text-fat`; tier or status colours as text go through `ink()` (`lib/colors.ts`); other fixed palette colours need a `dark:` pair (e.g. `text-amber-700 dark:text-amber-400`). Charts use `hsl(var(--token))`. **A chart over dates names the day in its tooltip** ("Monday, Oct 12"; the axis keeps the short "Oct 12"): its rows carry the day as `date` (YYYY-MM-DD) and its `Tooltip` takes `labelFormatter={dayLabel}` (`features/analytics/chartStyles.ts`, with `tooltipStyle` and `axisTick`).

**Background photo** (Settings → Theme → Background photo; `features/settings/wallpaper.ts`, `Wallpaper` mounted in App, `WallpaperCard`): a picture of the user's own behind the whole app. It is **per device and never synced**: the photo is shrunk once when picked (longest side 1600 px, JPEG, usually 80–300 KB) and kept as a data URL in the local-only Dexie table `wallpaper` (row `image`; row `look` = `{ dim, blur }`, apart so a slider doesn't rewrite the picture), which isn't in the backup and is wiped with everything else on sign-out. `Wallpaper` is one fixed layer under everything (the photo, then the theme's background colour at `dim` opacity: that overlay is what keeps text readable, so `dim` can't go below 40%) and sets `data-wallpaper` on `<html>`; `index.css` then makes `body` and **`bg-page`** transparent, cards (`bg-card`, not dialogs or sheets) slightly see-through and the sticky glass bars thinner. Bars only show where something scrolls under them, or they read as bands across the photo: the status bar's scrim (`status-scrim`) is hidden until the page has moved (`data-scrolled`, set by `Wallpaper`), and Home's search strip has no fill until it is actually stuck to the top (`useStuck` → `wallpaper-clear`; the field itself is a card like any other, and takes the card style). **A whole-screen fill must use `bg-page`, not `bg-background`**, or that screen hides the photo (the routine page and the sign-in page keep their own on purpose). The rank-up sequence and the share card ignore it.

**Card styles** (Settings → Theme → Card style; `features/settings/cardStyle.ts`, `CardStylePicker`): Solid (the default), Glass, Outline, Glow, Raised and Aura. A style is **only CSS**: `settings.cardStyle` (synced; read it through `cardStyleOf`) becomes `data-card` on `<html>` (painted from localStorage before React renders, like the theme, and followed by `useThemeSync`), and the rules for it in `index.css` restyle everything that is a card, which is everything with `bg-card`. No component knows which style is on, and a new card needs nothing. The rules leave three things alone: dialogs and sheets (`role="dialog"`); anything marked `wallpaper-solid`, which has to stay readable over whatever is behind it; and a `bg-card` inside a `bg-card`, which goes flat so it reads as part of the card around it (the cards inside a Settings row; that rule comes last and its class is doubled, so it outweighs every style's own). A style's edge is the `--card-edge` shadow, added to the element's own Tailwind ring and shadow, so no style changes a card's size. **Glass** needs something behind it: with a background photo that's the photo (the only case where cards get a `backdrop-filter` blur, and only real cards, not chips); without one, `Wallpaper` draws a soft glow in the theme's colours (`ambient-glow`, `data-wallpaper="glow"`), which is smooth already, so nothing is blurred per card and scrolling costs nothing extra. `data-wallpaper` is therefore "photo" or "glow"; rules that only care that the page is see-through test for its presence. "Reduce transparency" (the system setting) turns glass back into a solid card. **Raised** lifts cards off the page: on a dark theme, where a shadow can't show, that is a lit top edge and a surface a little brighter toward the top; on a light one mostly a soft shadow. **Aura** puts a thin line in the theme's gradient around each card (two offset inset shadows, since a real gradient border would change the card's size) with a faint glow. Both keep the shadow and the glow for real cards (`rounded-3xl` / `rounded-2xl`): chips get the edge only. Home's search field is `rounded-3xl` for that reason (on a 48 px field that is still a pill). Bold (thick outlines, hard shadows) was dropped in October 2026 for these two; a saved `bold` reads as Solid. A new style: an entry in `CARD_STYLES`, its rules in `index.css`, its small picture in `CardStylePicker` (drawn by hand, since the real rules hang off `<html>`), and the id in the `CardStyle` type.

**Avatar**: tap the Profile avatar to pick a photo; it's centre-cropped to a 160 px JPEG data URL (≈10 KB, `features/settings/avatar.ts`), stored in `settings.avatar` (synced) and shared in the leaderboard snapshot (`avatar`). No storage bucket. Anything drawn from a friend goes through `safeAvatar` (small raster data URLs only).

**Settings** tab (`/settings`): account & sync, leaderboard sharing, steps (Android app), reminders, workouts (tips switch, link to the plan), theme (palette, card style, background photo), bottom bar, home screen, app icon (Android app), backup, version (`APP_VERSION` in `SettingsPage.tsx`, now v0.4.0). **Every section is a collapsed row** (`SettingsSection`: icon, title, what's set now, chevron) that opens on a tap, so the page fits one screen; the cards inside are unchanged and sit on the row's own surface. A section opens by itself when its `#id` is in the URL (search results), and the ones left open stay open until the app restarts. A new section: wrap its card in `SettingsSection` with a one-line summary. **Profile** (`/profile`, from the Home header's profile button): name + photo, the day they started ("Started leveling up since: …"; `features/gamification/startDate.ts`: the first day food, a workout or a check-in was logged or an achievement earned, read from the data and stored nowhere, so it needed no column and every existing account has one; weigh-ins and steps don't count, since those arrive with older dates), level/XP, shortcuts, strength rank, leaderboard, achievements (goals + latest, expandable), then body & goals and daily targets as two collapsed rows (the same `SettingsSection` as Settings, with what's set as the summary).

**Fast food logging** (Nutrition): each meal offers **"Same as yesterday"** (its most recent version from the last 14 days) in one tap when empty, and a **Meals** sheet with saved meals (named sets of foods, `savedMeals`), recent versions of that meal, and "save this meal". An empty day offers **copy the day before**. The add-food dialog shows the four meals across its top (`MEAL_OPTIONS`; it opens on the meal it was called from, and from + that is only a guess from the time of day, so it can be changed there), **stays open** after each add (running "N added · kcal" bar with Undo and Done), starts each food at **the amount logged last time**, gives recent foods a one-tap **+** at that amount, and lists matching saved meals first. Favorites go into the current meal at their last amount. One-tap adds toast with **Undo** (`toastLogged`). Log through `logFoods` / `logMealItems` (`features/nutrition/logFoods.ts`), which run streak, XP and achievements once per batch. Tapping a logged food opens **Change amount or meal** (`EditFoodLogDialog` → `updateFoodLog`): the same grams / servings fields as adding (`FoodAmountFields`, `foodAmount.ts`) and the four meals, so a food under the wrong meal is moved instead of removed and added again. **The day on show** on Nutrition belongs to the visit (`useEntryState`; until one is picked it follows the clock): opened afresh, by its tab or by "Log food" from +, it is today, and Back finds the day that was being looked at. It used to sit in an app-wide store, and "Log food" then went to whichever day had been looked at last. **Creating a custom food** (`CustomFoodForm`) starts from what was typed in the search, needs only a name and calories (a macro left blank is 0), shows every field's error, and opens the new food's amount once saved. The bin beside it removes the food in one tap and toasts with **Undo** (`removeFoodLog`): undo logs it again as a new row, since the old id is already going out as a delete. **Quick add** ("+ Just calories" in the add-food dialog, `QuickAddCalories`) logs calories with no food behind them: it's a log of the built-in food `QUICK_ADD_FOOD` (1 kcal per serving, so 350 servings = 350 kcal, no macros), which keeps totals, sync, saved meals and copy-a-day unchanged. That food is kept out of every food list (`isQuickAdd`), reads "Calories only" in the meal, and its amount is edited as calories. **A custom food can be removed** ("Remove from my foods" under its amount in the add-food dialog, with Undo; `removeCustomFood`): the row isn't deleted but flagged (`Food.removed`, synced), because every total is worked out from the food behind each log and deleting it would empty the days it was eaten on. A removed food is left out of everything that offers foods (`useFoods`, Home search, saved and repeated meals, copy-a-day) and still read by everything that adds up a day; scanning its barcode again saves it afresh, which brings it back. A new list of foods to pick from must filter `removed` too.

**Online food search** (add-food dialog): under the foods on the device, a search of two letters or more offers "Search online for …" (`searchProducts` in `openFoodFacts.ts`, `useOnlineFoodSearch`, `OnlineFoodResults`). **Only on a tap, never while typing.** It asks the site's own Worker first (`GET /api/food-search?q=`, `worker/index.js`), which queries Open Food Facts' fast search (Search-a-licious: well under a second, any language, but no CORS headers, so a browser can't call it) and puts products sold in the visitor's own country first (`request.cf.country`; Vietnam and the USA are mapped). That was chosen over USDA's database because the users are in both countries: Open Food Facts has packaged food from both and takes Vietnamese text, needs no key, and is the same data the barcode scanner uses. The Worker's results carry values per 100 g only, so picking one fetches the product itself (`lookupBarcode`) for its package serving before the review. Where the Worker isn't there (the dev server, which answers `/api/*` with the app's HTML) or fails, it falls back to Open Food Facts' own search from the browser (`cgi/search.pl`), which is rate-limited (about ten searches a minute per address) and turns away about half of all requests at busy hours: searches keep 6.5 s apart and one that's turned away is asked again after the same wait (three tries, about 20 s at worst), then the row says so and offers to try again. Answers are kept until the app restarts. A product picked goes through the same review as a scanned barcode (the values are crowd-sourced) and is saved under its barcode id (`barcode-<code>`), so scanning it later finds it, and one saved before goes straight to its amount. To try the Worker locally: `npm run build`, then `npx wrangler dev`.

The date over the cards is a button with a calendar: any day up to the end of this week can be put on show, and the strip is then that day's week (`picked` in `HomePage`; until one is picked it follows the clock). *Today's Plan* shows the cards the user picked, in their order (`settings.homeWidgets`; unset = all): today's workout, steps, calories, water, creatine, the daily quest, macros, challenge, strength rank, leaderboard, streak/level (the trackers come before the quest: with the quest first they sat below the first screen). Tiles (steps, calories, water, creatine) pair two per row; a lone tile spans the row. **Customize** (Home header or Profile) edits the list. Add a new card in `features/dashboard/homeWidgets.ts` + `TodayWidgets.tsx`. `/home?log=steps` and `/home?log=water` open those sheets (app icon shortcuts)
- **Recap** (`/recap`, full screen; Week / Month / Year switch, `?period=week|month|year&start=YYYY-MM-DD`, old `?week=<Monday>` links still work; arrows step by the period; opens on the last finished week or month, and on this year so far, or last year in January; `features/recap/period.ts`): a week, calendar month or calendar year in review, all built by the same `buildRecap(period, start)` in `features/recap/recap.ts` and stored nowhere. Per-day figures count from the first day in the period with anything logged (`since`), and a month's or year's workout goal is the weekly goal pro-rated to those days. **Share as image** draws the recap onto a 1080×1350 canvas (`shareCard.ts`: always dark, header in the theme's accent gradient, name and photo, up to four stat tiles, overall rank with its emblem, new bests; **never food or body weight**) and hands the PNG to `lib/shareImage.ts`: the Android app's share sheet (`SoloPlugin.shareImage`), the Web Share API (browsers, iOS), else a download. The image is made when the dialog opens so the Share tap opens the sheet directly (iOS requires it). A headline, highlights (overall rank at the week's end vs going into it, lifts and runs that beat everything before the week), then tiles for workouts vs goal, training time, volume, cardio distance, steps, food (net kcal vs target, protein-target days), weight change, creatine and water days, each compared with the period before in the same neutral wording up or down, once the period is over (one still going isn't set against a whole one). `headline(recap, { shared: true })` is the line that leaves the phone (card, share text): it leaves food out. - **Search** (Home; Settings → Home screen can hide it, `settings.showSearch`, unset = shown): finds pages and their sections, quick actions, routines (yours + templates), exercises (logged lifts open their Strength progress chart, others their info sheet), foods (open the add-food dialog pre-filled, `?add=1&q=`), past workouts, challenges and friends. Accent-insensitive (`lib/search.ts`: `normalize`, `matchScore`); your own things rank above catalogue matches; groups are ordered by their best hit; Enter opens the top result. While open, results replace the Home cards. - **Routine detail / editor**, **active logger** (full screen, wake lock, rest timer, "Previous" column), **summary** (completion screen / history detail)

The workout is saved on that day and takes its place in the history by it (`startedAt` / `createdAt` become that day, at the hour it was entered); XP, bests and ranks are worked out as usual, and the streak is left alone, since it only ever counts today.
- **Editing past workouts**: the summary offers **Edit workout** for 7 days after the workout's date (`EDIT_WINDOW_DAYS`, `features/workouts/hooks/useEditWorkout.ts`). It reopens the logger with `draft.editing` set (no timer, rest timer or wake lock; sets load checked, Previous = the session before it). Save updates the workout and its sets in place, deletes unchecked/removed ones with `deleteSynced`, and recomputes kcal. It doesn't change XP (no farming), date or streak. The edit uses the draft slot, so it blocks starting a workout until saved or discarded.
- **Logger cards**: each exercise card **folds away** to its header (the chevron left of the name; `BlockDraft.collapsed`, kept in the draft so it survives a reload) and unfolds the same way. **Removing an exercise** takes it out at once and shows a toast with **Undo** for 7 s (`removeBlock` hands the block back, `restoreBlock` puts it where it was, sets and ticks included, as long as the same workout is still open). A card **folds itself** a moment after its last set is ticked (the store's `foldWhenDone`, called after every tick; not while editing a past workout, where ticks are only being corrected). Both kinds of card (lifts, cardio) are built on one shell, `BlockCard`: the header, the note and Replace, then the card's own fields. **Any set can be removed**: tapping its number turns the row into "Remove set N" for 4 s (two taps, so a stray one costs nothing), and a set that had something in it comes back with Undo (`restoreSet`); an exercise's only set can't go. **Replace** (beside the note, in `BlockCard`) swaps the exercise for another in the same place, for when the machine is taken (`replacementBlock`, store `replaceBlock`): the picker opens on the old exercise's category, the new card keeps the rest time and as many sets as were still to do, with the new exercise's own numbers from its last session, and sets already ticked stay logged under the old exercise as their own folded card. Undo for 7 s; not offered while editing a past workout. **Hold to move** (`useHoldToMove`, store `moveSet` / `moveBlock`): a set held for 0.4 s (anywhere on its row but the fields and the tick) lifts and is carried to another place in its exercise; an exercise is held by its name, and while one is in the air every card folds to its header so the workout fits the screen (nothing is saved as folded). It starts as an ordinary touch, so a swipe from the same spot still scrolls; once lifted, the page stays put, except near the top or bottom edge, where it scrolls under the item. Letting go isn't a tap on what was held (the click is swallowed). The header's arrows stay, and Alt + ↑ / ↓ on a set or a name moves it one place, since a hold-and-drag can't be done from a keyboard. The "Previous" column stays with the position, not the set. The hook is general (a `relative` list whose children are the items): **destructure what it returns**, because the lint rule takes the whole object for a ref once one of its members is passed to `ref`.
- **kg or lb per exercise**: the heading of the weight column is a small kg / lb switch (`UnitToggle`). **Stored weights are always kg** (ranks, charts, bests and the leaderboard never see pounds); the switch only says how that exercise's card shows and takes them. The choice is `ExerciseNote.unit` (the note's row, synced; unset = kg), copied into `BlockDraft.unit` when the block is made (`blockHistory`). Inside a block the weight fields are text **in the block's unit**, while `lastSets` / `trend` stay kg, so everything crossing that line goes through `features/workouts/units.ts`: `weightKg` when saving, `weightText` when prefilling or loading an edit, `lastSetsIn` for the Previous column and the hint, `setsInKg` for live ranks. Switching **converts** the fields (60 kg reads 132.28 lb) instead of reinterpreting them, so the real weight never changes by a tap; `fromKg` picks the shortest pound number that stores back to the same kg, which is why 135 lb comes back as 135 and a look at a kg lift in pounds doesn't nudge it. The summary's exercise list shows a pound-logged exercise in pounds (`useLbExercises`); everything else stays kg. A new place that reads or writes a draft weight must convert, or pounds get saved as kilos.
- **Exercise notes**: every exercise can carry one note of your own (seat height, pin, grip, cues). `ExerciseNote` shows it in the logger card (lifts and cardio) and in the exercise info sheet; tap to write, it saves on leaving the field. Stored in `exerciseNotes` (id `note-<exerciseId>`, synced; clearing saves `text: ''`), not on the exercise row, because built-ins are re-seeded on every start and never synced. Private: never in the leaderboard snapshot.
- **Exercise history**: the info sheet (an exercise's name in the logger, a routine, or search) ends with the exercise's past (`features/workouts/exerciseHistory.ts`, `ExerciseHistory`): its best set (highest est. 1RM, plus the heaviest when that's another set; most reps, longest hold, longest distance and fastest pace for the other kinds) and the last five sessions set by set, in the unit the exercise is logged in.
- **Share a workout** (any workout's summary: the header's share icon in history, and the **Share workout** button in both views; `features/workouts/shareCard.ts`, `ShareWorkoutDialog`): **the summary screen itself as a picture**, with the user's name and photo on top: the same cards in the history view's order (the figures and the body map, rank ups, new bests, every exercise set by set, lb where it's logged in lb), laid out in CSS pixels at the screen's own sizes on a 390-wide page and drawn 1080 px wide, as tall as the workout needs (drawn smaller past 16 million pixels, iOS's canvas limit). It follows the theme (its tokens resolved to rgb; tier text mixed by `--ink` as `ink()` does) but not the background photo or card style. The figures come from `summaryStats` (shared with `WorkoutSummaryCard`) and the body map from the same shapes and constants as `MusclesWorked`, so a change there shows on both. **The workout's notes, heart rate and calorie estimate stay off it** (`summaryStats(…, { shared: true })`; the owner's call). In history the bests and rank-ups are worked out on the fly, so Share waits for them. The preview in `ShareImageDialog` scrolls for a tall image.
- **Muscles worked** (summary card; `musclesWorked.ts`, `MusclesWorked`): the bodygraph's two figures with each muscle filled in the accent by how much that workout gave it (1 per set for a primary muscle, ½ for a secondary one; a cardio entry weighs one set per ten minutes, up to six), and the five most worked named beside them. It answers "what did today touch", not the volume radar's accounting: front delts count as helpers here, though the core as a helper (bracing) counts in neither.
- **Progression hints** ("tips"; `features/workouts/progression.ts`, `ProgressHint` in the logger card; lifts only, hidden while editing a past workout, and switched off altogether by Settings → Workouts → Tips during workouts, `settings.workoutTips === false`): from the last session, double progression. Add reps at the same weight until every set at the working (heaviest) weight reaches the rep target, then take the next weight up. Rep target = the routine's reps, else 8 barbell compounds / 10 other compounds / 12 single-joint / 15 small raises. The jump = the smallest gap between the lifter's own working weights on that exercise (`trend.step`), else an equipment default (barbell 2.5, 5 for heavy squats/deadlifts; dumbbell 1 under 10 kg, else 2.5; machine 5; cable 2.5; kettlebell 4). Because the same step is a far bigger share of a light lift, the reps to reach before a jump are whatever Epley says keeps the heavier weight in range, at most target + 5 (so a 10 kg curl builds to 17 before 12.5 kg, a 60 kg bench jumps at its target). Bodyweight moves count bodyweight in the load (reps-only ones add a rep, then "make it harder"); assisted ones progress by taking help off. After 4+ weeks away it says to ease back in (10% lighter, 15% after 8 weeks); three sessions at the same weight without more reps suggest a ~10% reset. An exercise logged in pounds is worked out **in pounds** (jumps of 5 lb on a bar, 10 on a stack, 2.5 or 5 on dumbbells; targets on the 2.5 lb grid), and its text and fill are pounds too. **Use** fills the numbers into the sets not done yet (`fillSets`), never done ones. Block history (`blockHistory`) stores `lastSets` + `trend` in the draft when the block is created. Sources and reasoning are in the file header; exercise classes are matched by name, so a new exercise type may need a keyword there.
- **Cardio is not sets.** Exercises with `type: 'cardio'` are logged as one entry: time, optional distance, effort (Easy/Moderate/Hard, saved in `rpe`). Pace and kcal update live. Routine editor asks for a duration only; routine time uses that duration. kcal = each cardio entry's MET (by speed when distance is logged, else by effort; `lib/cardio.ts`) + the rest of the session at the lifting MET. Summary shows cardio time/distance/pace; new bests include longest distance and fastest pace. Timed holds (plank, `defaultUnit: 'min'`, not cardio) stay as sets with one "min" column.
- **Analytics**: three tabs, **Muscles** (the set-volume radar), **Strength** (weekly tonnage, est. 1RM) and **Food & body** (macro adherence, body weight, steps); see *Tabs* under Ranks. **Weekly analysis / set volume** radar (sets per muscle for a Mon–Sun week vs. RP volume landmarks: yellow below MEV, orange growing, green sweet spot = MAV, pink overreaching; the training level scales the targets (×0.75 beginner, ×1.25 advanced): it follows from when the user started training, `settings.trainingSince` (Profile → Body & goals, and the first-run setup; `levelSince`: under a year beginner, one to three intermediate, more advanced, so it moves on by itself), and only without that date is it the toggle on the card (`settings.trainingLevel`); "Customize radar" picks the muscles, min 3; "i" opens the MEV/MAV/MRV guidelines; list with a bar per muscle), weekly tonnage, est. 1RM progression (**Strength progress**: chips for the 12 most-trained lifts plus a search over every logged lift, `LiftPicker`; `?lift=<exercise id>` preselects one), macro adherence, body weight, steps. A set counts 1 for each primary muscle and ½ for each secondary (`features/analytics/volume.ts`; secondary "Core" and front delts don't count)
- **Ranks** (`/ranks`): three tabs, **Overview** (overall rank, Bodygraph, muscle rankings), **Lifts** (every ranked lift, running rank) and **Progress** (the weekly chart, how ranks work). **Tabs** (`usePageTab`, here and on Analytics; the pages were four to six screens long): the tab is the one last looked at, until the app restarts; a link to a section (`#id`, as search results use) opens the tab that section is on (the page's `SECTION_TAB`), and so does `?lift=` on Analytics. Picking a tab is not a navigation, and only the open tab's sections are mounted. In all: overall rank, ranked **Bodygraph** (anatomical front/back wireframe, ~30 muscle shapes per side mapped to the 19 ranked regions; ranked muscles glow in their tier colour, tap for detail; shapes in `bodygraphShapes.ts`, half-figure mirrored), muscle rankings (6 groups, "2/3 ranked"), **running rank**, weekly rank-progress chart (overall, groups, running), every ranked lift with its next-division target, how ranks work. Trophy button → leaderboard
- **Leaderboard** (`/leaderboard`, from Profile, the Home card and Ranks): boards for Strength (overall rating), Running (5K-equivalent), This week (workouts, then minutes; resets Monday) and Level (by `totalXp(level, xp)`: `userStats.xp`, and so the snapshot's `xp`, only counts into the current level and starts again at each level-up, so ranking by it alone put a level 2 above a level 9), top three on a podium; **muscle crowns** (who holds the top rank in each group + running); recent highlights (new bests from the last 14 days). `/leaderboard/:id` (or `me`) is a friend's profile: overall badge, level, streak, their Bodygraph, **head to head** with you, both rating lines over 12 weeks, this week, **their routines**, best lifts. **Sharing routines** (`features/leaderboard/sharedRoutines.ts`, `SharedRoutines`): every routine travels in the snapshot (`routines`: no notes, and custom exercises described inline, since a friend's device doesn't have them), so it needs no table and follows the sharing switch. On a friend's profile each opens to its exercises and **Add to my routines** copies it, unplanned; **Use their week** copies their planned routines onto their weekdays and frees those days in your plan (one routine a day), your routines all staying. A friend's routines are untrusted JSON: read them only through `cleanSharedRoutines` (lengths cut, numbers clamped, unknown kinds defaulted). A copied custom exercise reuses one of yours with the same name and kind, a built-in included, before making a new one. Your own entry is always built live from local data; friends' come from the server (cached in localStorage for offline)

Full-screen routes (no nav) use `components/FullScreen`. All screens must respect safe areas (`pt-safe`, `pb-safe`, `env(safe-area-inset-*)`).

**Screens scroll the document**, never a fixed-height inner container: use `min-h-dvh`, not `h-dvh` + `overflow-y-auto`. iOS Safari (browser and home-screen app) mis-sizes fixed-height shells and can hide the bottom nav behind its toolbar. Sticky headers carry their own `pt-safe`; a global scrim covers the status bar; `ScrollToTop` resets scroll on navigation; bottom sheets are capped to the screen height in `ui/sheet.tsx`. **No scrollbar is shown anywhere** (the owner's call: a bar down the side reads as a web page): `index.css` hides them for every element, and the Android app's own bar, which is the WebView's and ignores the page's CSS, is switched off in `MainActivity`.

**Picking a date** is always the same calendar (`components/DatePicker`: a button that opens a dialog with a month grid, a Today button, and Clear where the date can be left out), so no screen makes you step to a day one at a time: the day on show on Home and Nutrition, the recap's period and the set-volume week (a day picked shows the week, month or year it falls in), a weigh-in's date, when a workout was done, when you started training. The grid itself is `components/MonthGrid` (Monday first; tapping the month's name swaps the days for the twelve months of a year, with arrows for the year, so a date years back is a few taps), which History's calendar is built on too. **Where its icon goes:** the button is a flex row, so the calendar icon sits on the text's line, 8 px from it at least: after the text where the button is a form field (at the field's right end, in the same box as `Input`) or a heading, before it where the date is centred in a bar, alone in a 40 px button beside arrows. Don't use `<input type="date">`: it looks and works differently in every browser and WebView, and its icon can't be placed. `min` / `max` grey out what can't be picked (a weigh-in or a workout can't be dated ahead; Home stops at the end of this week).

**Dialogs and the keyboard**: `DialogContent` centres itself in, and is no taller than, what the keyboard leaves in view: `--visible-top` / `--visible-height` (defaults in `index.css` = the whole page). The Android app shrinks the page itself for the keyboard (`100dvh` follows, nothing else needed); iPhones and Chrome only shrink the visual viewport, which `useVisibleViewport` (App) measures into those two variables. A dialog taller than that scrolls inside itself, so one with buttons under a list has to be a flex column where the list is the part that gives way (`AddFoodDialog`: the list is `h-[300px] min-h-[7.5rem] overflow-y-auto`, everything else `shrink-0`), or the buttons end up below the fold the moment the keyboard opens. Use a plain scrolling `div` for such a list. (The Radix `ScrollArea` wrapper is gone: its `h-full` viewport didn't follow a shrunk flex item in WebKit.)

## Data Model (Dexie schema)

Defined in `src/db/schema.ts`, currently at **version 18**. When changing it, bump the version and write a migration (`.stores({ table: null })` to drop a table). Never silently mutate the schema.

```ts
// Synced collections (key: uuid string)
foods, foodLog, bodyMetrics, dailyActivity, achievements, savedMeals (remote `saved_meals`: name, items [{foodId, servings}], mealType),
exerciseNotes (remote `exercise_notes`: one row per exercise, id `note-<exerciseId>`, `text`; '' = cleared; `unit` 'kg' | 'lb' = the unit it's logged in),
exercises (built-ins seeded, only custom ones sync), workouts, workoutSets, routines, challenges,
checkins (daily habits: `creatine-YYYY-MM-DD` tick, unticking sets done = false; `water-YYYY-MM-DD` with `amount` in ml; `quest-YYYY-MM-DD` done = that day's quest XP was given)
// Synced singletons (id = 1)
userStats, targets, settings
// Local-only
workoutDrafts (id = 1, the in-progress workout), pendingDeletes (sync tombstones), wallpaper (the photo behind the app on this device + how it's shown)
```

- **Index dates as ISO strings** (`YYYY-MM-DD`) for day-level queries; store timestamps as `number` (`Date.now()`).
- IndexedDB can't index booleans. Filter (`.filter(r => r.isFavorite)`) instead of `where('flag').equals(1)`.
- Per-day rows use deterministic ids so two devices don't create duplicates: `weight-YYYY-MM-DD`, `steps-YYYY-MM-DD`, `ach-<key>`.
- Seeded singletons use `updatedAt: 0` so a fresh device always adopts the server copy.
- **The catalog** (built-in foods and exercises) is written to the database only when it changed: a build carries a fingerprint of `src/data` (`VITE_CATALOG`, set in `vite.config.ts`), the device remembers the one it wrote (`solo:catalog`), and `seedDatabase` skips the ~590 rows when they match (it used to write them before every first screen). The stamp is dropped when sync pulls food rows, because a built-in made a favorite lives on the server as it was saved and a pull puts that older copy back. While developing it's always written.

## Sync (Supabase)

- **Offline-first:** Dexie is the source of truth on-device.
- **Writes:** stamp `updatedAt: Date.now()`, set `syncPending: true`, then call `requestSync()` from `lib/sync.ts`. **Deletes:** use `deleteSynced(table, remoteName, uuids)`, never a bare `table.delete()`, or the row comes back from other devices. A pushed row always says `deleted: false`: one with a fixed id (a weigh-in's is its date) that is deleted and then written again would otherwise stay deleted on the server and vanish at the next pull. `logWeight` also drops that day's pending delete; the two together are what make Undo for a removed weigh-in hold.
- **Sync run:** push pending rows → push tombstones → pull by server cursor (`serverUpdatedAt`, keyset-paginated, 5-min overlap). Pulled rows never overwrite a newer pending local edit. A sync requested mid-run re-runs afterwards. Sync also runs on sign-in, reconnect and app foreground.
- **Server:** `supabase/migrations/20260921000000_sync_v2.sql` defines the base tables; later files in that folder add to it (run in filename order). Collections are keyed by `(user_id, uuid)`, singletons by `user_id`. A trigger stamps `serverUpdatedAt` and ignores stale writes (last-write-wins). RLS: `user_id = auth.uid()` on every table. Columns are camelCase (quoted) because rows sync as-is.
- **Adding a synced field:** add it to the TS type, the column list in `lib/sync.ts`, and a new idempotent migration (`add column if not exists`). PostgREST rejects unknown columns, so keep all three in agreement.
- **Accounts:** data on a device belongs to one account (`solo:localOwner`). Signing in as a different account wipes local data first; signing out wipes it too (with a warning if changes are unsynced). Local-only data is adopted by the first account that signs in. **A launch doesn't wait for the session** (`useAuthInit`): when that key says an account's data is on the device, the app shows it at once (`userId` is set from the key; `session` follows) and the session is settled behind it. Checking a session means renewing it over the network once its hour is up, which held every such launch on a spinner, and offline ended on the sign-in screen after 10 s. Until the session is real nothing syncs, Settings says "Waiting for a connection", and only a sign-out (the library's `SIGNED_OUT`, or no stored session at all) sends the app to the sign-in screen: "couldn't check" never does. So `userId` means "this account's data is on screen" and `session` means "and we can talk to the server": gate screens on `userId`, server calls on the session.
- **Auth:** email + password (magic links don't work inside iOS home-screen apps, and Supabase's built-in mailer only reaches org members). Accounts are created in the Supabase dashboard; public sign-up is disabled.
- **Keep-alive:** a GitHub Action pings the DB every ~3 days so the free project doesn't pause.
- **Reminder push** (`supabase/migrations/20260930000000_reminders_push.sql`): `push_subscriptions` and `push_queue` aren't synced collections either; they're written directly (see *Reminders*). The same file adds `settings.reminders`.
- **Leaderboard** (`supabase/migrations/20260925000000_leaderboard.sql`): not a synced collection. Table `leaderboard` has one row per user (`displayName`, `visible`, `snapshot` jsonb, `updatedAt`); RLS lets every signed-in user read visible rows and only the owner write theirs. `useLeaderboardPublisher` (mounted in App) rebuilds the snapshot after each successful sync and upserts it only when it changed. Sharing off (`settings.shareOnLeaderboard === false`) publishes `visible = false` with an empty snapshot. Snapshots are versioned (`v: 1`); readers must tolerate missing fields. The snapshot carries the profile photo (`avatar`), so photos need no leaderboard column.

## Gamification Layer

1. **Streaks**: a day counts as "logged" when food **or a workout** is logged. One streak freeze per ISO week (max 2 banked), tracked on `userStats.freezeWeek` so it's granted once across devices. Freezes are consumed automatically on missed days (`lib/streak.ts`).
2. **XP & Levels**: workout finished +50, +2 per set, +25 per new best (est. 1RM), rank-ups (see 5); daily kcal target within ±10% +30; protein target +20; daily quest +40 (see 7). Level curve: `xpForLevel(n) = 100 * n^1.5` (`lib/xp.ts`).
3. **Achievements**: 48, declarative in `features/gamification/achievements.ts` in six categories (training, strength, cardio, consistency, nutrition, daily habits). Each is a `metric` and a `target`: it unlocks when the number reaches the target, and the same pair is its progress ("12 / 50 workouts"). `achievementStats()` reads the numbers (workouts, sets, tonnes lifted, distinct exercises, routines, rank ratings, longest run, cardio km, streak, level, food days, protein days and longest protein run, weigh-ins, step/water/creatine days); it loads each source once and only when a metric from it is asked for, so `evaluateAchievements` (`lib/achievementEval.ts`) only reads what the still-locked ones need. A new achievement is one row in the list (plus a metric there if it counts something new); **keys are permanent** (`ach-<key>` rows), titles can change. Keep them about showing up and getting stronger, never eating or weighing less. Call sites announce through `announceAchievements` (one toast each, one summary toast when more than three unlock at once, "Goal reached" for a goal). **Profile → Achievements** (`AchievementsSection`): closed, it shows the goals and the three latest unlocked; "Show all" opens every one by category with a progress bar on the locked ones; tapping one opens a sheet with its progress and **Set as goal**. Goals are `settings.achievementGoals` (keys, synced, at most 3; earned ones drop off), shown first with their progress (`useAchievementProgress`, live).
4. **Personal challenges**: user-set target + deadline (workouts, steps, volume, food-logged days, protein days); progress computed from local data. **Personal only.** Shared challenges are a possible future feature.
5. **Strength ranks** (inspired by LiftOff): every set gets a 1–1000 rating from its est. 1RM (Epley, reps capped at 20), bodyweight reps (added weight counts through the same capped Epley, so long weighted sets don't snowball), or hold time, against standards for the lifter's **sex and bodyweight on that day** (`features/ranks/standards.ts`, `scoring.ts`). Nine tiers (Wood → Olympian, 100-pt bands from 200) × three divisions, **climbed I → II → III** (`DIVISIONS` in `tiers.ts`: I is where a tier starts, III is its top, and past III comes the next tier's I, so Platinum III → Diamond I; until October 2026 they ran the other way, at the owner's request they now match the number of gems). **A division is marked by gems under the helm**: as many as the division's number (one for I, two for II, three for III), in the tier's colour (`divisionGems` in `badgeArt.ts`), so the emblem grows as a tier is climbed. `RankBadge` takes `division` and draws the helm a little smaller to make room; pass it wherever a rank, not just a tier, is shown (the ladder of tiers and the standings, which only know a tier, don't). Emblems under 34 px have none (they'd be specks), nor has Olympian, which has no divisions; the share card's emblem (`badgeImage`) follows the same rule. Each tier's emblem is a different helmet, more elaborate the higher it goes (nasal helm, Corinthian, great helm, plumed centurion, crystal warden, kabuto with crescent and diamond, war king with greatswords crossed behind, their gold hilts up by the crown, a gold collar and a crown, obsidian dread lord, and for Olympian a faceted crystal helm with a gold sun on the brow, great feathered wings, a halo and a sunburst), drawn from declarative flat-shaded layers in `ranks/components/badgeArt.ts`. Platinum and up glow; the halo strength comes from `--badge-glow` / `--badge-glow-outer` (stronger on light themes so it shows). The five reference levels rate beginner 200, novice 350, intermediate 500 (Platinum, the median lifter), advanced 700 (Champion), elite 900 (Olympian, top 5%); past elite, one more advanced→elite gap reaches 1000 (`LIFT_LEVELS` in `scoring.ts`). A lift's rank is its best set ever (ranks never drop). Each standard lists the **muscle regions** it ranks (19 regions in 6 groups: chest, shoulders, arms, back (lats, upper back, traps, lower back), core, legs (quads, hamstrings, glutes, adductors, outer hips = glute med/min + TFL, calves)); a region takes its best lift, a group its best region, overall = weighted mean once 3 groups are ranked. Ranks are absolute (vs. standards, not vs. other users), so they work the same for any number of users. Derived on-device, nothing stored or synced. Rank-ups toast live in the logger, show on the summary, and give XP (+30 per lift division, +75 per overall division). Needs `settings.sex` + one weigh-in. Only built-in exercises with a standard are ranked; add more in `standards.ts` (own data or `like` + factor; a `like` only borrows a weight standard, so a bodyweight move gets its own `reps` entry). Eccentric (slow-lowering) versions of the squat, bodyweight squat, bench press, pull-up, push-up and dip were added in October 2026: the weighted ones borrow their lift at 0.8–0.85, the bodyweight ones take fewer reps than the full move (negatives more, since they're easier). Weight conventions the standards assume: dumbbells/kettlebells = one bell; barbells include the bar; stack machines = the pin number; cables = effective weight (halve on 2:1 pulleys). "Chest-Supported Machine Row" (`ex-chest-supported-row`) is the machine; the dumbbell version is `ex-chest-supported-dumbbell-row`. "Back Extension (Hyperextension)" is the bench (bodyweight + added weight); the seated stack machine is `ex-machine-back-extension`. **Running rank** (`running.ts`, separate from overall), scored for active adults, not competitive runners: every Running / Treadmill Run entry of 5 km+ at running pace (≥ 7 km/h) scores its pace as a 5K-equivalent (Riegel, exponent 1.06) on a 5K scale by sex, **plus a distance bonus** (+90 per doubling past 5 km: 10K +90, half +187, marathon +250, capped). Calibrated so a 6:00 /km half marathon is Diamond (men) and outstanding runs reach Olympian. The same score **ranks the legs** (`LEG_CREDIT`: calves 100%, quads 95%, hamstrings 85%, glutes 80%) whenever it beats the muscle's best lift (region `topLift` = "Running"). Live in the cardio card ("Pace like a 27:31 5K, +187 for 21.1 km"), toasts, rank-ups on the summary. **The bars** (`ranks/components/RankProgress.tsx`, `RankRing.tsx`): the overall rank shows the whole tier and not just the division. On the Ranks screen that is a ring around the emblem (`RankRing`: three quarters of a circle, open at the bottom, one arc per division, so done, under way and still to come read at a glance; Olympian is a single arc to 1000); on Home's card it is the straight bar, `TierProgress`. In both, both ends are named (this tier, the next), the divisions on the way are marked as milestones, it is never drawn empty, and the fill brightens toward a glowing tip whose colour moves from this tier's toward the next one's. Those first three are what writing on progress bars agrees on (a goal in sight, small steps, a start already made); nothing found says a gradient itself reads better, so that part is the look the owner asked for. Every other rank bar is `RankProgress`, one division, coloured the same way. A stroke can't carry a gradient along a curve, so the ring's fill is short pieces, each a shade further on, shown through a mask that is one stroke along the whole ring: filling it and moving it are then one number (the mask's dash), and the tip is drawn at the ring's start and turned to its place. The shared colouring is `.bar-fill` in `index.css` (a faint start, a full-colour tip); the XP bar uses it too (`gamification/xpFill.ts`), at its old size.
6. **Rank-up sequence** (`features/ranks/components/RankUpCeremony.tsx`; one scene = `RankUpScene`, the light show = `RankUpEffects`, order and timing = `rankUpCeremony.ts`): finishing a workout that moved a rank opens the summary with a full-screen sequence, one scene per rank-up. `ceremonyQueue` picks at most three lifts (or the running rank), smallest first, and ends on the overall rank; the rest are only in the summary's list. In a scene the old emblem (greyed out for a first rank) shakes while a ring fills around it, a flash throws it off, and the new one lands with its name, XP and division pips (~3.5 s for a new tier or a first rank, ~3.2 s for a division, a little longer for overall). The stage is **always dark**, like the share card: the tier colour carries the rays and the glow, and the logo's chevrons rise behind. **Three presses anywhere skip the rest** (`useTriplePress`: taps, clicks or Enter / Space / Escape, at most 0.7 s apart; a single press must never skip, since it only plays once). It plays once per workout (`solo:rankUpSeen` in sessionStorage) and not at all under `prefers-reduced-motion`. The summary mounts only when it ends (`useRankUpIntro`), so the hero and confetti still play; every row of the summary's Rank ups list has a replay button, in history too, which is also how to see a scene without earning one. Mid-workout rank-ups stay a toast: a full-screen takeover between sets would be in the way. Steps with `times` there use `ease: 'linear'`, because the browser eases a whole opacity timeline rather than each step and fades would start early.

7. **Daily quest** (`features/gamification/quest.ts`, `useDailyQuest.ts`, Home card `QuestCard`): a few things to do today, all taken from what the user already tracks, and +40 XP for clearing every one. Objectives: **move** (a workout logged, or the step goal reached), **protein** target reached (without a protein target: any food logged), and **water** / **creatine** when those cards are on Home. Never calories: a quest must not be a reason to eat less. **Nothing happens when it isn't cleared**: no penalty, no mark on the day, a past day's card just says what was done. `useDailyQuestReward` (App) watches today's quest and pays it the moment the last objective is done, whatever finished it (a set, imported steps, a glass of water); the payment is a check-in row `quest-YYYY-MM-DD`, so it syncs and is given once. The card is a normal Home card (`quest`); a Home customized before it existed gets it added under the trackers once per device (`solo:questCard`), and removing it sticks; a saved Home that had it above the trackers, where it used to go, has it moved under them once per device (`solo:questBelowTiles`, `questBelowTiles` in `homeWidgets.ts`), and moving it back up sticks.

### Weight trend and what the logs say you burn

**Trend** (`lib/weightTrend.ts`): the scale moves a kilo from day to day on water and food, so the weight page and the Analytics weight card draw the weigh-ins as dots and a smoothed trend as the line (`withTrend`: each day the trend moves a tenth of the way to the scale, further at once after a gap). The pace shown beside it ("−0.2 kg a week") is the slope of the best-fit line through the last 28 days of weigh-ins (`weightSlope`: it doesn't lag the way the smoothed line does), in the same neutral wording up or down.

**Adaptive calories** (`features/nutrition/expenditure.ts`, shown in Profile → Body & goals by `ExpenditureNote`): energy out = energy in − what the change in weight is worth (7,700 kcal per kg), over the 28 days before today. It needs 14 logged food days and 4 weigh-ins spread over 14 days; until then the card says how far along it is and the suggestion comes from the formula (`targetSuggestion.ts`: Mifflin-St Jeor × activity). Once it's there, **Apply suggested targets** uses the measured figure as maintenance (minus what walking accounts for, while steps are subtracted day by day), with the same goal offsets as before (cut −500, bulk +300). Two guards, because it's only as good as the food log: days far under the person's usual intake are left out as half-logged, and an estimate below 1.1 × resting is set aside as an incomplete log (the formula is used, and the card says why). Targets never change by themselves: the user applies them.

### First-run setup

An account that has never saved a setting gets five short screens before the app, right after its first sign-in (`pages/WelcomePage`, `features/setup`): name and photo; sex, height, weight and when they started lifting; goal and workouts a week; **what to track**; the theme. Everything is optional and the whole thing can be skipped; either way it doesn't come back. There's no flag for it: `useNeedsSetup` reads `settings.updatedAt === 0`, the row every fresh device is seeded with, and finishing or skipping writes the settings (stamping it), which syncs. Signed in, it waits for the first sync to finish, since until then a new device can't tell a new account from an old one whose settings haven't arrived. **Nothing is saved until the end**, because any write to settings ends the setup: the photo is held in the form (`AvatarPicker`'s `onPick`), and a theme tapped is only painted as a preview (`paintTheme(…, false)`; skipping puts the saved one back). "What to track" lists the Home cards that are trackers (`TRACKABLE`: steps, calories, water, creatine, macros) as a checklist with **steps, calories and water already ticked**, so a new user has a working Home without deciding anything; what's ticked becomes `settings.homeWidgets` (Home's usual order, minus the trackers left out). Finishing saves the name, photo, sex, height, training start, goal, weekly workout goal, theme and Home cards, logs the weight as today's weigh-in, and sets suggested targets when sex, height and weight are all there. The goal defaults to Maintain. Units are kg and cm.

### Step calories

Steps come off the calories eaten: **net kcal = eaten − step burn**, shown against the baseline kcal target (Home calories tile, Nutrition header, week strip ring, Analytics dots, kcal-target XP). On by default; Profile → Daily targets switches it off (stored in the legacy `settings.dynamicTargetsEnabled`: unset = on, read it with `countsSteps`). Burn (`lib/stepCalories.ts`) is the **net** cost of walking, since the target already covers resting: 0.5 kcal × body kg × km (ACSM walking equation; measured ≈ 0.53 and independent of BMI/body fat), km = steps × 0.414 × height. Weight = the weigh-in on or before that day (else the first one after, else 70 kg); height from Profile (else 170 cm). 10,000 steps ≈ 245 kcal at 70 kg / 170 cm. Carbs and fat targets grow by the burn in the baseline ratio; protein stays (`lib/macroTargets.ts`). Suggested targets use ×1.375 instead of ×1.55 while steps are subtracted, so walking isn't counted twice. **Workouts are never subtracted** (no reliable way to measure them; owner's call). Everywhere a target is shown, use `useCalorieBudget` (dashboard hooks) and `netKcal`. Don't read the raw baseline.

### What the web platform can't do (don't promise it)

- **Heart rate / sleep**: there's no web API for Health Connect or Apple Health. Heart rate is an optional manual field on a finished workout; calories burned are a MET-based **estimate** (`lib/workoutMath.ts`), always labeled "est.".
- **Reminders on iOS** only reach the installed home-screen app (16.4+), by web push; Safari tabs can't get them. See *Reminders*.
- **Steps**: manual entry on the web and iOS (no step-counter API). The **Android app** imports them from Samsung Health (see *Android app*).

### Reminders

Settings → Reminders: six kinds (`REMINDERS` in `features/reminders/reminders.ts`: workout, creatine, food, weigh-in, water, weekly recap), each a switch and a time; workout also "every day" or "days with a routine". Stored in `settings.reminders` (synced; `reminderPrefs` reads it and carries over the old workout-only `reminderEnabled/Time/Days`). **Whether a device shows them is per device** (`useDeviceNotifications`), never synced; a fresh install of the Android app asks to show notifications by itself and switches that phone's reminders on if allowed (see *Android app* → Steps).

- **The plan is made on the device.** `planReminders` lists the nudges for the next 14 days (`PlannedReminder`: key `kind-YYYY-MM-DD`, time, text, url). Today's is left out once the thing is done (creatine ticked, food logged, weighed in, water goal met, a workout logged or in progress); the weekly recap fires on Mondays. `useReminderScheduler` (App) re-plans when the settings or today's state change, on foreground, on reconnect and at midnight, and hands the plan to `deliverPlan`, which skips unchanged plans.
- **Android app**: `@capacitor/local-notifications` (`lib/localNotifications.ts`) schedules them on the phone (ids 100000+; exact alarms via `USE_EXACT_ALARM`), no server. **Creatine and water** go to the app's own notifications instead (`QuickLog.kt`, `SoloPlugin.scheduleQuickLog`; an APK without it falls back to the plugin), which carry a **Tick it off / Add a glass** button that logs without opening the app: the plugin's buttons can only open it. The button queues `QuickLogWorker`, which loads the site off-screen like the step sync with `{ kind, date }` on `window.SoloBackground.task()`; `main.tsx` runs `features/reminders/quickLogTask.ts` (tick only, never untick; water + one glass to the reminder's day), syncs, and the answer replaces the notification. The job has no network condition: offline the page comes from the service worker's cache, the log is saved on the phone and syncs when the app is next opened (waiting for a connection left the "working" notification spinning). A load error on that page isn't final: offline with the service worker asleep, WebView reports `ERR_INTERNET_DISCONNECTED` for the main frame and then delivers the page from the cache a moment later, so the worker gives the page 10 s to answer after an error before saying it couldn't log (only the live https site does this, not a localhost build: test offline against production). Alarms are kept in SharedPreferences and set again after a restart or an update (`QuickLogReceiver`). The rest timer uses the same plugin (id 9001) so it rings when the phone is locked; with the app on screen it's cancelled just before it fires.
- **Browsers and the iOS home-screen app**: web push. The device subscribes with `VITE_VAPID_PUBLIC_KEY` (`push.ts`) and saves the subscription in `push_subscriptions`; every signed-in device writes the plan to `push_queue`; pg_cron runs `sl_send_due_pushes` every minute, which deletes the due rows and posts them to the `send-reminders` Edge Function (it only signs and sends: no database access, no service key). `src/sw.ts` shows the push and, on tap, opens the reminder's url (`open-url` message → `useNativeLinks`). Without the VAPID key in the build, push isn't offered. Setup steps are in README.
- A new reminder kind: add it to `ReminderKind`, `REMINDERS`, and its "done today" fact in `useReminderScheduler`. Keep the wording neutral and the default **off** (no nagging, no guilt).

**Haptics** (`lib/haptics.ts`): `tap()` on a set checked off, a cardio entry logged and creatine ticked (Android vibrates; iPhones tick through a hidden switch input, iOS 18+, and only from inside a touch); `buzz()` when the rest timer ends (Android only).

## Coding Conventions

**TypeScript**: strict; no `any` (use `unknown` and narrow). `type` for unions/intersections, `interface` when extension is expected.

**React**
- Function components only. Hooks live with their feature.
- Keep components under ~150 lines; extract subcomponents or hooks past that.
- Side effects belong in hooks. Don't call `setState` synchronously inside an effect, and don't call `Date.now()` / `new Date()` during render. Use `useNow()` (the React hooks lint rules enforce most of this).

**State**: persistent data flows through Dexie via hooks backed by `useLiveQuery`. Zustand holds UI/session state only (the active-workout draft is mirrored to Dexie for crash safety).

**Styling**
- Tailwind + theme tokens in `index.css` (`bg-card`, `text-muted-foreground`, `primary` = the theme accent, orange in Ember). Primary buttons are `foreground` pills (`Button` default: white on dark themes, near-black on light); the accent is for highlights, progress, and active states.
- Mobile-first (~390px). Touch targets ≥ 44px. Inputs must be ≥ 16px font (iOS zooms otherwise).
- Dark (Ember) is the default theme and the design target, but every screen must also read on the light themes: follow the colour rules under **Themes** (no raw white/black on surfaces, `ink()` for tier text, `dark:` pairs for fixed palette colours).

**Motion**: short and in CSS. Something opening by its height is `components/Collapse` (a grid row from 0fr to 1fr; what's inside is mounted only while it shows, and padding goes on the content, not on `Collapse`, or it can't close to nothing): Settings rows, logger cards, muscle groups, the custom theme's colours. `Segmented`'s pill and the bottom bar's marker slide (one element moved by `transform`); a tab screen slides in from its side and a tab's content fades in when picked (`key` restarts it). Home's search results drop in from under the field, group after group, while Cancel slides in beside it (it is always rendered, `inert` when closed, so the field gives way instead of jumping). **A toast's button works over an open dialog or sheet**: toasts carry `pointer-events-auto` (Radix switches pointer events off outside a modal) and `DialogContent` / `SheetContent` don't take a press on a toast for a press outside (`keepOpenForToast` in `lib/utils`), so an Undo can be offered from inside one. Entrances use tailwindcss-animate (`animate-in fade-in-0 slide-in-from-…`), or `animate-fade-in` where there are fixed bars inside, because any transform on an ancestor, even the identity one `animate-in` uses, unpins them for as long as it runs; a tick lands with `animate-pop`; a ring's arc is `.ring-arc`. **A progress bar fills up once each time the app is opened, never again while moving between tabs**: its fill takes `ref={useRise(id)}` (`hooks/useRise`; rank and XP bars, rings, goals, challenges, water, calories and macros). The hook plays the fill (Web Animations, so no class or key is involved; what it animates from is its second argument: a `width`, a `left`, a ring's `arc`, or a `turn`) the first time a bar with that name shows on that page, and after that the bar is simply there. "Opened" is a launch or coming back after 30 minutes away, when whatever is on screen fills again. It also holds the element's own CSS transition back for its first 0.6 s, because most bars arrive at 0 and get their number once it has been read, and sliding up to it was a fill on every visit. Bars that share a name (a list of lifts, the rings on Home) rise together. Around 200 ms, ease-out, `transform` and `opacity` where possible. "Reduce motion" is honoured once, globally, in `index.css` (everything still changes, nothing travels). framer-motion is for the few set pieces that need it (the rank-up sequence, the summary's hero, the rest banner) and **must not be imported by anything the first screen loads** (see below).

**Loading fast**: what every launch has to download and run is the entry file, `vendor` (React, the router, Dexie, Supabase, Zustand: named in `vite.config.ts` so it only changes when they do, and a release re-downloads the app's code alone) and the small shared files Vite lists as `modulepreload` in `dist/index.html`: about 880 KB, 273 KB gzipped (it was 1.44 MB in one file). Three things are kept out of it, and each comes straight back with one careless import: **recharts** (a fifth of the app: only screens loaded with `lazy()` may import it, which is why Home's weekly chart is lazy), **framer-motion** (so the shell, the progress ring and Home's cards animate in CSS), and **the catalog** (`data/foods*`, `data/exercises*`: imported only by `db/seed.ts`, dynamically; the two constants screens need live in `data/basics.ts`). After a change that touches imports, build and check that `dist/index.html` preloads no `CartesianChart-`, `proxy-`, `foods-` or `exercises-` file. Measured on a phone-like browser (CPU ÷4): the first screen on a cold slow-4G load went from 3.4 s to 2.8 s, and a normal launch's first card from 0.61 s to 0.49 s. **Opening a screen** is the other half. Every screen but Home is its own file (`lazyAhead` in `App.tsx`, not plain `lazy`): Home opens with what it needs, and from 0.8 s later the others are fetched one by one in idle moments (`lib/lazyAhead.ts`; from the service worker's cache on a normal launch; skipped on a data-saver connection; a failure is silent and must not trigger the reload that a failed navigation does), so by the time a tab is tapped its code is here. And a screen is **never put on show before it has something in it**: `AppShell`'s `Suspense` boundary sits *outside* the keyed, animated `<main>`, so a screen whose code is still on its way keeps the one on show where it is (a navigation is a React transition, which only waits for boundaries that are already up) and then arrives with its slide. With the boundary inside, the slide played on an empty screen and React, which holds a fallback it has shown for 300 ms, brought the content in after it: every tab's first open, about 350 ms. **Don't put a `Suspense` inside something that is keyed by the route.** Measured (CPU ÷4): a tab's first open now takes 40 to 60 ms from the tap, with its content, and 240 ms for Analytics tapped the instant Home appears. **The launch screen** is the mark in the middle of the page, drawn by `index.html` itself (inside `#root`, in the colours of the theme last used: `solo:launch`, written by `applyTheme` and read by an inline script, since no app code is here yet) and then, identically, by `App.tsx`'s `LaunchScreen` while the account is checked; it turned the first paint of a normal launch from 320 ms of blank into 110 ms. Keep the two alike. There is deliberately no loading screen on coming back to an app that is still in memory: nothing loads then, so it would only be a wait.

**Naming**: components `PascalCase.tsx`, hooks `useThing.ts`, utilities `camelCase.ts`.

**Shared helpers** (an audit in October 2026 found each of these written out two to seven times; use the one that exists): a date as `yyyy-MM-dd` is `toDateStr` / `today` (`lib/date`); one decimal is `round1` (`lib/format`); `clamp`, `swapped` (two list items trading places) and `moved` (one item taken to another place) are in `lib/utils`; a time as `5:30` or `1:02:10` is `formatClock` (`lib/cardio`); a logged set as text is `describeSet` (`features/workouts/describeSet.ts`); a draft field from a stored number is `numText`, and cardio's one entry is `cardioSet` (`features/workouts/types.ts`); avatar letters are `initials` (`features/settings/avatar.ts`); accent-insensitive matching is `normalize` (`lib/search`); a food measured in g or ml is `usesGrams` (`features/nutrition/foodAmount.ts`); the body figures' wireframe constants live beside the shapes (`bodygraphShapes.ts`); an emblem tone is `toneColor` (`badgeArt.ts`); "run now and each time the app comes back to the front" is `useRefreshOnReturn`. The stat tile with an icon is `components/IconTile`. A date is picked with `components/DatePicker`; the four meals for a control are `MEAL_OPTIONS` (`features/nutrition/logFoods.ts`).

**Imports**: use the `@/` alias; no deep relative paths.

## Android app

The owner's phone runs a Capacitor shell (`android/`, `capacitor.config.ts`) whose WebView loads the **live site**, so web deploys reach it with no reinstall and one codebase serves both platforms. Friends on iOS keep the PWA; nothing native runs there.

- **Native-only code** checks `isAndroidApp()` (`lib/native.ts`: Capacitor injects `window.Capacitor` into the app's WebView) and **imports its plugin lazily**, so it never loads in a browser. Keep it that way: a static import of a native plugin is harmless but wasted bytes for iOS. **Never let a promise resolve to a plugin object** (returning one from an `async` function, or from a `.then`): a Capacitor plugin is a proxy that answers every property, so the promise calls `Plugin.then()`, which rejects with "not implemented" and the feature silently does nothing. Box it (`{ api: plugin }`) or hand out plain functions, as `lib/localNotifications.ts` and `soloPlugin()` do. This only shows in the app, so test native paths in the emulator (README → Dev).
- **Steps** (`features/health`): `useHealthStepsSync` (App) imports the last 14 days from Health Connect on launch and whenever the app returns to the front (at most every 2 min), once step access is granted in Settings → Steps (`HealthStepsCard`, shown only in the app). Health Connect totals each local calendar day across sources without double counting. A day's row (`steps-YYYY-MM-DD`, via `writeSteps`) only changes when the import is **higher**, so manual entries are never lowered. Samsung Health must share steps with Health Connect (its Settings → Health Connect). **A fresh install asks for everything the app uses, by itself** (the owner's call; Android forgets every permission when the app is removed, and each used to be found again in Settings). Once the app proper is open (signed in, or local mode: never on the sign-in screen, where nothing may be written yet), `useHealthStepsSync` asks in turn for notifications (which also switches that phone's reminders on), the camera (a WebView has no way to ask for it but to open it, so it is opened and closed at once; only a secure page has a camera, so a dev build must load `http://localhost` through `adb reverse` to see this), step access, and background access **if the account says that was on** (`settings.health`: `{ background }`, synced, noted when the switch is flipped or the phone is seen to have it on; `features/health/healthPrefs.ts`): it is a feature to switch on, not something the app needs. Each question is asked **once per install** (`firstAsk`, `solo:healthAsked`) and never again after a no, since Android stops showing a question after two refusals and Settings has to keep its chance. Notifications are only asked while Android hasn't been (`prompt`): where they are already allowed, the reminders switch is the user's.
- **Permissions**: Health Connect `READ_STEPS`, plus `READ_HEALTH_DATA_IN_BACKGROUND` for the background sync. capacitor-health's manifest declares 12 more read permissions, which `AndroidManifest.xml` strips with `tools:node="remove"` (the remote site runs with the app's permissions, and Health Connect lists every declared one), so to read another type, delete its remove line. Also `CAMERA` (barcode scanner), `VIBRATE` (rest timer, haptics), `USE_EXACT_ALARM` and the notification plugin's own (`POST_NOTIFICATIONS`, boot restore). The plugin's rationale activity opens `privacy_policy_url` (`res/values/strings.xml` → `public/health-privacy.html`; without it the activity crashes). minSdk 26.
- **The app's own plugin** (`SoloPlugin.kt`, reached through `soloPlugin()` in `lib/native.ts`; `Capacitor.isPluginAvailable` is false in an APK built before it, and the UI then says to update the app). It carries the long-press **shortcuts** (and takes the ones to show, `setShortcuts`), switches **background step sync** on and off, shares images (`shareImage`, through the FileProvider's cache path), takes the quick-log reminders (`scheduleQuickLog`) and hands Android's **Back** to the site (`handleBack`, `leaveApp`). Methods added after an APK was built answer `UNIMPLEMENTED` there (`isUnimplemented`); callers fall back or ask for an update.
- **Step sync while closed** (Settings → Steps → "Sync in the background"; `StepsSync.kt`, `StepsSyncWorker.kt`): needs Health Connect's `READ_HEALTH_DATA_IN_BACKGROUND` (asked for when switched on). About once an hour WorkManager reads the 14 day totals from Health Connect natively, then loads the site in an off-screen WebView with them on `window.SoloBackground`; `main.tsx` sees that bridge and runs `features/health/backgroundSteps.ts` instead of drawing the app (same raise-only write as the open app via `stepsWriter.ts`, then a normal sync, then a one-line result shown in Settings). This way the data and the sign-in session stay in the WebView's storage, where they already live. The job skips itself while the app is on screen.
- **Shortcuts** (long-press the icon): chosen in Settings → App icon, up to four of the nine in `features/settings/appShortcuts.ts` (`settings.appShortcuts`, synced; unset = Start workout, Log food, Log weight). They're **dynamic** shortcuts: `useAppShortcuts` (App) sends the choice to `SoloPlugin.setShortcuts` on launch and on change, and `Shortcuts.kt` publishes them (it also publishes the default three once, before the site first loads). Each is a `solo://open/<path>` intent; the plugin emits a `shortcut` event (kept until the site listens) and `useNativeLinks` navigates. An APK from before this still has its three fixed ones, and the card says to update (`soloHas('setShortcuts')`). A new shortcut needs its entry in `appShortcuts.ts`, its drawable (`scripts/generate-shortcut-icons.mjs` draws `ic_shortcut_<id>.xml` from the Lucide glyph) and a line in `Shortcuts.kt`'s `ICONS`. Installed PWAs on Android get a fixed three from the web manifest's `shortcuts` (a manifest can't differ per user).
- **Back** (the edge swipe or the button; `hooks/useAndroidBack.ts`, mounted in App): Capacitor's shell has no Back handling of its own, so the system's Back simply left the app from any screen. `SoloPlugin` now owns an `OnBackPressedCallback`, off until the site calls `handleBack({ enabled: true })`; each Back then arrives as a `back` event and the site decides, in this order: whatever asked to close first (`useCloseOnBack(open, close)`, used by Home's search), then an open dialog, sheet or menu (the same Escape that closes it from a keyboard, so the rank-up sequence still needs three), then one screen back: **Home from a bottom-bar screen**, the previous screen from a deeper one (the logger included: the workout keeps running), and **out of the app from Home** (`leaveApp` → `moveTaskToBack`, the app stays alive). With no listener (the page is loading or was reloaded) the callback steps out of the app itself, so Back is never a dead key. An APK from before this keeps the old behaviour (`soloHas('handleBack')`). Something new that Back should close and that isn't a Radix layer: give it `useCloseOnBack`.
- **Notifications**: reminders and the rest timer (see *Reminders*). Small icon `ic_stat_ascent`.
- **WebView limits**: no file downloads, so backup **Export** tells you to use a browser in the app (Import works through the file picker).
- **Import timing**: `importSteps` waits for any running sync (`syncService.whenIdle`) and does each day's read-compare-write in a Dexie transaction, so a higher number typed on another device isn't overwritten by a stale local copy.
- **Status bar**: edge-to-edge with see-through bars; `applyTheme` calls `setSystemBarStyle` so the icons stay readable on light themes. Safe areas work through the same `env(safe-area-inset-*)` CSS.
- **Build**: `npm run android` (web build → `cap sync` → Gradle debug APK → `solo-leveling.apk`, gitignored). Rebuild only after native changes (plugins, permissions, icons via `scripts/generate-icons.mjs`, `capacitor.config.ts`). The app module has Kotlin (the root `build.gradle` carries the Kotlin Gradle plugin; `kotlin_version` in `variables.gradle` keeps the plugins on the same one).

## What NOT to Do

- Don't widen **sharing** beyond the leaderboard snapshot without being asked. Food, body weight, notes and raw logs stay private (RLS). Routines are in the snapshot at the owner's request (October 2026), without their notes. Anything new in the snapshot must be something a friend would reasonably expect to see.
- Don't add ads, analytics, telemetry, or third-party trackers.
- Don't add paid services or anything that breaks the $0 budget. Flag it instead.
- Don't add guilt mechanics or aggressive notifications (no red ✗ for missed days, no shame UI).
- Don't add aggressive calorie restriction features, weight-loss-focused defaults, or before/after framing. Keep nutrition tracking neutral.
- Don't add achievements tied to extreme restriction. Reward consistency and progress.
- Don't refactor wide swaths of the codebase without being asked. Make surgical changes.
- Don't add dependencies without flagging them first.
